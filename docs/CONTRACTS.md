# חוזה החיבור — לקרוא לפני כתיבת קוד

## מה מוכן ומה לא

האתר ריק. אין פעולות ספרייה ממומשות. מוכנים רק React, טעינה אוטומטית של מסכים ונתיבי שרת, חיבור SQLite, טיפוסים ונתוני דוגמה. אין `localStorage` כמקור אמת ואין API שמחזיר הצלחה פיקטיבית.

הטיפוסים המדויקים נמצאים ב־[types.ts](../src/shared/types.ts); מבנה הטבלאות ב־[schema.sql](../fixtures/schema.sql). לא משנים אותם בלי אישור המנחה. לשמות השדות ב־SQL וב־JSON יש אותו איות.

## כללי עבודה במקביל

לכל אחת שני אזורי קוד בלבד:

- `src/features/NN-name/` — מסך `Page.tsx` עם `export default`, CSS Modules, בדיקות ועזרים מקומיים.
- `server/features/NN-name.ts` — `export default` של Express Router. אפשר גם פונקציות named exports המוגדרות בכרטיס.
- בדיקות שרת בקובץ `server/features/NN-name.test.ts`.

משימה 05 לא צריכה מודול שרת. אין ליצור קבצים עבור משתתפת אחרת. לא עורכים את App, טעינת השרת, הטיפוסים, החבילות או קובץ הנעילה. תלות חדשה מחייבת אישור המנחה.

React מגלה אוטומטית מסכים בתבנית `src/features/*/Page.tsx`; השרת טוען אוטומטית קבצים בתבנית `server/features/NN-name.ts`. אין קובץ registry שכולן צריכות לערוך. שרת Express אינו נטען מחדש תמיד בעקבות יצירת קובץ חדש: אחרי יצירת מודול שרת, עצרי והפעילי שוב `npm run dev`.

### התחברות למסד בשרת בלבד

ייבוא `db` מתוך `../db` במודול שרת. אין לייבא `sql.js`, `node:fs` או מודול שרת לקוד דפדפן. SQLite נשמר ב־`data/library.sqlite`, מחוץ לגיט. SQL תמיד עם פרמטרים, לא עם שרשור קלט.

משתמשים ב־sql.js, מנוע SQLite ללא קומפילציה מקומית. החיבור המוכן מספק `db.prepare(sql).get(...params)`, `.all(...params)`, `.run(...params)`, `db.exec(sql)` ו־`db.transaction(() => { ... })()`. התוצאות הן רשומות SQL; יש לאמת/להמיר אותן לטיפוסים. הטרנזקציות סינכרוניות בלבד. כל כתיבה מוצלחת נשמרת לקובץ דרך החלפה אטומית; כשל שמירה נזרק ולא מדווח כהצלחה.

יש להפעיל תהליך שרת אחד בלבד מול קובץ מסד מסוים. sql.js טוען את המסד לזיכרון ואינו מתאם כתיבה בין תהליכים. אין להריץ פקודת הכנת נתונים בזמן שהשרת עובד.

### חיבור למסכים

הנתיב הוא `#/NN-name`. לכרטיס ספר: `#/04-book?id=book-1`. לכרטיס תלמידה: `#/08-student-card?id=student-1`. למסך המדבקות אפשר להעביר `?bookId=book-1`.

כל מסך מציג כותרת, קישור `#/03-catalog`, וקישורים הקשורים לתפקידו. אין צורך לבנות תפריט ראשי בכל מסך. לצילום יש הדמיות עם מעטפת מלאה; המעטפת אינה חובה במשימת המשתתפת. המנחה יכולה לחבר מעטפת אחידה לאחר מיזוג הפיצ׳רים.

## HTTP

ב־Router כותבים `/books`, לא `/api/books`: השרת מוסיף `/api`. בלקוח קוראים `fetch('/api/books')`. אין להגדיר CORS פתוח. שני השרתים מאזינים ל־127.0.0.1 בלבד.

גוף בקשה מסוג JSON עם `Content-Type: application/json`. השרת מאמת כל קלט גם אם הטופס כבר בדק אותו. זמני הצלחה: GET/PATCH/PUT/פעולה 200, יצירה רגילה POST 201. צרכנים חייבים לקבל כל 2xx.

תשובת שגיאה בכל הנתיבים:

```json
{ "error": { "code": "INVALID_INPUT", "message": "יש להזין כמות שלמה בין 1 ל־100" } }
```

| HTTP | שימוש |
|---|---|
| 400 | שדה או תאריך לא תקינים |
| 404 | מזהה לא מוכר |
| 409 | ברקוד/מזהה כפול, עותק שכבר מושאל, החזרה חוזרת, מגבלת השאלות |
| 500 | כשל לא צפוי; יש לרשום אותו בשרת ולהציג הודעה |

בכל fetch בודקים `response.ok`. כשל אינו רשימה ריקה ואינו הודעת הצלחה. כפתורי שמירה מנוטרלים בזמן הבקשה. ב־GET מציגים טעינה, שגיאה ומצב ריק בנפרד.

## ישויות וכללים

- `Book`: כותר בקטלוג. שם וגיל יעד הם השדות בגרסה זו, בלי מחברת או ISBN.
- `Copy`: עותק פיזי אחד עם ברקוד ייחודי. `LIB-000001` הוא קוד בן 10 תווים.
- `Student`: מזהה פנימי UUID, ובנפרד `schoolId` בית־ספרי ייחודי. אין שימוש במספרי זהות אמיתיים.
- `Loan`: שייכת לעותק ולתלמידה. `returnedOn=null` פירושו השאלה פעילה.
- `Settings`: שורה יחידה ב־SQL עם id=1; ב־JSON אין צורך בשדה id.

מצב עותק נגזר מהשאלה פעילה; אין שדה `status` בעותק או בספר. המסד מונע שתי השאלות פעילות לאותו עותק. אי־אפשר למחוק היסטוריה כדי להחזיר ספר.

תאריכים: YYYY-MM-DD, תאריכים אמיתיים ללא שעות. תאריך הלקוח הוא מקומי, לא `toISOString()` שעלול לשנות יום באזור הזמן. איחור: השאלה פעילה עם `dueOn < today`; יום ההחזרה עצמו אינו איחור. הוספת ימים חייבת לעבוד במעבר חודשים ושנים. returnedOn לא מוקדם מ־borrowedOn.

## חוזים בין בעלות המשימות

הרשימה המדויקת של ה־HTTP נמצאת בכרטיסי המשימות. שני שיתופים בצד השרת:

1. משימה 02 מייצאת `addBooks(items: BookInput[]): string[]` מתוך `server/features/02-intake.ts`. התוצאה היא מזהי העותקים שנוצרו. היא פועלת בטרנזקציה ולא תלויה ב־Express request/response. משימה 10 קוראת לה, לא משכפלת אותה.
2. משימה 07 מייצאת `saveStudent(input: StudentInput, id?: string): Student`. בלי id נוצרת תלמידה; עם id מתבצע עדכון, או 404 אם אין תלמידה כזאת. משימה 06 בודקת schoolId קיים, ומפעילה את הפונקציה בתוך טרנזקציה של כל הייבוא.

אל תיצרי קובץ של בעלת משימה אחרת כדי לגרום לייבוא לעבור. אפשר לפתח את המסך, הפענוח והבדיקות באמצעות mock ב־Vitest, או לבקש מהמנחה למזג את ה־PR המקדים. כתבי בדיקת אינטגרציה אמיתית לאחר המיזוג. אין mocks אוטומטיים במוצר.

### קריאות JSON

- `GET /books` → `{ items: CatalogItem[] }`; רשומה לכל ספר, לא לכל עותק.
- `GET /copies` → `{ items: CopyView[] }`; תומך ב־bookId אופציונלי.
- `GET /books/:id` → `BookDetails`.
- `GET /students` → `{ items: Student[] }`.
- `GET /students/:id/card` → `StudentDetails`; לא לבלבל עם עריכת תלמידה.
- `GET /scan/:barcode` → `CopyView`.
- `GET /loans` → `{ items: LoanView[] }`.
- `GET /settings` → `Settings`.
- `GET /backup` → `LibraryData`.

## קליטת ספרים

BookInput מכיל title, ageGroup, quantity ו־targetBookId אופציונלי. יצירת ספר ללא targetBookId; הוספת עותקים לספר קיים רק עם targetBookId מפורש. הכמות לא נשמרת בשדה בספר — היא מספר רשומות העותק שייווצרו.

ברקודים מוקצים רק ב־addBooks של 02. מסך המדבקות ב־05 רק מציג אותם. הקוד הבא גדול מהמקסימום הקיים, עם בדיקת גבול; אין איחוד אוטומטי לפי שם. כל הבקשה אטומית.

## ייבוא אקסל

read-excel-file/browser בצד הלקוח; אין צורך להעלות את קובץ האקסל עצמו לשרת. אחרי בדיקה ושלב אישור שולחים JSON. בשרת מאמתים שוב. קבצי הדוגמה ב־public/workshop/samples; שמות העמודות קבועים.

- ספרים: `שם ספר | גיל יעד | כמות עותקים`.
- תלמידות: `מזהה תלמידה | שם מלא | כיתה`. עמודת מזהה בפורמט טקסט.

שם ספר וגיל זהים מצביעים על התאמה אפשרית, לא אישור לזהות. המשתמשת בוחרת אם להוסיף עותקים לקיים. ייבוא ספרים חוזר עלול להוסיף עותקים נוספים — מזהירים, לא מציגים אותו כפעולה נטולת כפילויות.

## בדיקות ומוכנות

כל משתתפת מוסיפה בדיקות רק בתחום שלה. אפשר לפתוח SQLite זמני בזיכרון ולטעון את fixtures/schema.sql ואת fixtures/demo.sql בבדיקות; לא לגעת ב־data/library.sqlite של הספרנית.

`npm test` בודק כרגע את התשתית בלבד. מעבר בדיקות התשתית אינו מעיד שהמוצר נבנה. המוצר נחשב מוכן להדגמה רק אחרי מסלול הקבלה ב־FACILITATOR.md.
